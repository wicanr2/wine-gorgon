# 002：位址空間與 API 攔截

- 狀態：`READY`（M1a 已交付：`internal/win16` ＋ `cmd/nemap`）
- 日期：2026-09-05

## 1. selector 配置

| selector | 內容 | 備註 |
|---|---|---|
| `(段號 << 3) \| 7` | NE 的段 | 刻意讓 `sel >> 3` 就是段號，除錯時不必查表 |
| `0xF00F` | API thunk | 每個相異匯入佔 4 byte |
| `0x8007` 起，每次 +8 | 動態配置（`GlobalAlloc` 之類） | M2 才會用到 |

段的配置量取 `max(檔案內容長度, MinAlloc)`：資料段的檔案內容通常比它要求的
空間短（後面是 BSS），程式碼段反過來。

## 2. API 攔截

匯入的重定位目標一律填成 `0xF00F:(索引 × 4)`。CPU 看到 `CS == 0xF00F`
就知道這是一次 API 呼叫，用位移反查是哪一個——**攔截點與匯入清單是同一份
資料**，不會漂。thunk 段裡那幾個 byte 填 `0xCB`（`retf`），只是讓「萬一真的
被解碼執行」有定義的行為。

## 4. 兩件量出來才知道的事

### 4.1 這支執行檔沒有多節的重定位鏈

NE 的非加法式重定位可以是**鏈結串列**：被修補的 word 原本存的是下一處的位移，
`0xFFFF` 結束。CIV.EXE 的 10,429 條**全部**是單節——Borland 的 TLINK 一筆
只寫一處。

早期版本拿「修補位置數 == 重定位筆數」當成「鏈沒走」的警訊，在這支執行檔上
**誤報**。修法不是拿掉檢查，是把加法式與鏈結式分開數，並且**另外寫一個有
多節鏈的合成映像**（`loader_test.go` 的 `buildChained`）去覆蓋那段程式碼——
真檔跑不到的路徑，只靠真檔驗證會讓它永遠沒有覆蓋。

### 4.2 所有匯入都是序號式

`IMPORTNAME` 是 **0** 筆。157 個匯入全部是 `模組 + 序號`，執行檔裡根本沒有
`BITBLT` 這種字串。

所以 API 實作層的鍵是 **(模組, 序號)**，不是名字。IDA 顯示的
`GLOBALALLOC`／`BITBLT` 那些名字來自 IDA 自己的 Win16 序號表，不是這個檔案
提供的——**那是一份外部對照表，要自己維護一份並且說得出它從哪來**。

## 5. 已知還沒做

- `INTERNALREF` 目標段號 `0xFF`（movable segment 的間接進入點）目前直接報錯
  而不是靜靜填 0。CIV.EXE 沒有這種重定位；真的碰到時要先解進入點表。
- `OSFIXUP`（329 筆，WIN87EM 的浮點修補）目前一律指向 thunk 段位移 0。
  沒有 FP 模擬器時，執行到那裡會是一個看得懂的錯，而不是算出錯的數字。
