# 006 — 和原版逐點比對

## 1. 參考幀是什麼

civ1 專案的 `workplace/test-output/win31-new-game-unit-v1/screens/root-main-map.png`：
DOSBox 裡的 Windows 3.1、**800×600**、1:1 沒有縮放，畫面上是剛開局的
主地圖（4000 BC、巴比倫、Settlers），旁邊還有 `World Map` 與 `Status`
兩個視窗。同一個目錄裡的 `NEWUNIT.SAV` 是那一刻存下來的存檔。

**用存檔而不是重跑開局**：世界是亂數生成的，重跑一次不會得到同一個世界。
載入那份存檔才能保證兩邊在比同一件事。

## 2. 兩個必須先弄對的轉換

### 2.1 6 位元 DAC

VGA 的調色盤 DAC 每個通道只有 6 位元。應用程式給的 8 位元值進到硬體時
被截掉低 2 位，螢幕上看到的是展開回來的值。參考幀是螢幕擷取，所以它
記錄的是**量化之後**的顏色。

展開方式是**位元複製**（`x<<2 | x>>4`），不是 `x*255/63`：

| 遊戲給的值 | 位元複製 | 乘除截斷 | 參考幀 |
|---|---|---|---|
| `(1,128,1)` 草地 | `(0,130,0)` | `(0,129,0)` | **`(0,130,0)`** |
| `(0,73,128)` 海洋 | `(0,73,130)` | `(0,72,129)` | **`(0,73,130)`** |
| `(74,50,16)` 棕 | `(73,48,16)` | `(72,48,16)` | **`(73,48,16)`** |

差一個位元就足以讓每一個像素都判定為不同。

### 2.2 RealizePalette 不收攏

Windows 的 `RealizePalette` 在文件上會把「和靜態色完全相同」的邏輯項
收攏到那一格。**原版上實測是不收攏的**：邏輯索引 i 一律落在實體索引
`10+i`。

證據兩份：

1. civ1 專案在原版上量到「圖集索引 ＋ `0x0A` ＝ 實體調色盤索引」
   （`docs/re/313`–`316`）。
2. 直接比對：收攏之後灰階多佔一格，後面所有顏色往前位移一格，地形變成
   紅橙雜訊；不收攏之後海洋 `(0,73,128)`、草地 `(1,128,1)`、丘陵
   `(142,103,28)`，和參考幀量到的值逐項吻合。

`Process.CollapsePalette` 留著給將來真的需要收攏的程式用，預設關閉。

## 3. 結果（`已證實`）

### 3.1 整塊客戶區

把地圖客戶區能重疊的最大一塊（440×538 ＝ **236,720 個像素**）逐點比對：

```
比對 440x538 ＝ 236720 個像素：不同 54（0.0228%）
```

那 54 個像素全部集中在 `(398..402, 297..305)`，內容是 `(255,255,255)`
對 `(0,0,0)`——**參考幀上的滑鼠游標**。游標是 Windows 畫的，不是遊戲畫的；
這一層沒有畫游標。扣掉它，整塊客戶區逐點相同。

### 3.2 地圖內容

```
$ nediff -a-rect 260,247,96,96 -b-rect 428,266,96,96 ours.png oracle.png
比對 96x96 ＝ 9216 個像素：不同 0（0.0000%）
逐點相同
```

那 96×96 是這一幀上**全部有內容的地圖區域**（其餘是未探索的黑色）：
海岸線、草地與丘陵的抖動、以及中央的 Settlers 單位盒。9,216 個像素
全部相同。

判定用的是 RGB 完全相等，沒有容差、沒有縮放、沒有「近似相同」。

## 3.3 視窗幾何（`已證實`）

三個視窗的位置與客戶區和參考幀逐項相同：

| 視窗 | 視窗矩形 | 客戶區 |
|---|---|---|
| `CIVILIZATION`（類別 `CIV`）| (168,0) 632×600 | (171,41) 610×540 |
| `World Map`（`WdwSmMap`）| (0,0) 168×127 | (3,22) 162×102 |
| `Status`（`WdwStatus`）| (0,244) 168×356 | (3,266) 162×331 |

要同時對上這三個，`SM_CXFRAME` 與實際保留的邊框必須**分開**：

- 遊戲拿 `GetSystemMetrics(SM_CXFRAME)` ＝ **4** 去算「我要多大的視窗」
  （小地圖要 160×100 的客戶區 → 開出 168×127）。
- Windows 實際扣掉的非客戶區是 `SM_CXDLGFRAME` ＝ **3**
  （168 − 2×3 ＝ 162 的客戶區）。

兩邊都用 4：客戶區小 2 個像素、原點偏 1。兩邊都用 3：遊戲會把視窗開小
2 個像素。只有分開才對得起來——而這一點是**量出來的**，不是文件上的。

## 4. 落點：已解（2026-09-05）

橫向曾經差 **168–169 個像素**，縱向差 1。橫向那一個已經解掉，而且和
「小地圖整片是黑的」是**同一個 bug**。

### 4.1 病因：視窗 DC 的幾何被凍在 GetDC 當下

`newWindowDC` 原本把 `w.ClientX/Y/W/H` 抄進 DC 就不再更新。而 CIV.EXE
的做法是：

```
CreateWindow "CIV"      位置 (0,0) 600x400     ← 先建一個小的
CreateWindow "WdwSmMap" 位置 (20,20) 40x40
...                                            ← 中間拿 DC 存起來
MoveWindow  → CIV (168,0) 632x600、WdwSmMap (0,0) 168x127
```

然後用**同一個 DC** 畫。凍住的話：

- 主地圖：DC 原點停在建立時的客戶區 `(3,41)`，而正確的是 `(171,41)`
  ——畫出來的東西整個往左 **168 px**。
- 小地圖：DC 的裁剪停在建立時的 `(23,42)-(57,57)`（40×40 視窗的客戶區
  35×16），而正確的是 `(3,22)` 162×102 ——`DrawSmTiles` 的 160×100 blit
  幾乎整片被裁掉，client 於是全黑。

兩個症狀差很遠，各自被當成不同的謎追了好幾輪。**Windows 的視窗 DC 本來
就是跟著視窗的可見區域走的**，凍住那一刻的幾何是模擬層自己加的假設。

### 4.2 修法與驗收

`p.dc()` 取出視窗 DC 時重算原點與裁剪（`refreshWindowDC`）；`BeginPaint`
的更新矩形改存**相對客戶區**的值（`DC.ClipRel`），視窗一移動就跟著移。
回歸測試：`TestWindowDCFollowsMoveWindow`、`TestPaintDCClipStaysRelative`。

修好之後對 civ1 的 DOSBox 參考幀（`root-main-map.png`）：

| 區域 | 結果 |
|---|---|
| World Map client `(3,22)` 162×102 | **逐點相同** |
| 主地圖 client（位移 `(1,1)`）500×400 取樣 | 不同 290（0.15%），全在海浪色帶上 |

### 4.3 那 `(1,1)`：邊框用錯了 `SM_CXDLGFRAME`

剩下的 `(1,1)` 不是內容問題，是**客戶區原點差 1 px**。病因是
`frameFor` 對 `WS_THICKFRAME`／`WS_DLGFRAME` 用 `SM_CXDLGFRAME`（3）
而不是 `SM_CXFRAME`（4）。當初選 3 的理由是「量到的客戶區是 162×102」
——**那是量錯了**：框最內側那一道線是黑的，未揭露的地圖格也是黑的，
量黑區的時候分不出來（civ1 的 DS327 §3 用同一張幀逐點掃過，結論相同）。

改用 4 之後三件事同時閉合：

- 小地圖：視窗 168×127 → 客戶區 **160**×100，和遊戲自己配置的
  160×100 緩衝區一模一樣。
- 主視窗：(168,0) 632×600 → 客戶區原點 **(172,42)**，正是參考幀上 tile
  內容的起點。
- 客戶區寬 632 − 4 − 4 − 16 ＝ **608** ＝ 19 格 × 32，與遊戲算出來的
  視窗寬度閉合。

### 4.4 結果：主地圖與小地圖都逐點相同

掃過海浪與閃爍兩個相位之後（`scripts/blink-phases.txt` 同法）：

| 區域 | 結果 |
|---|---|
| 主地圖 client `(172,42)` 608×538 ＝ 327,104 px | **只差 54 px**，就是原版截圖上的滑鼠游標（Windows 畫的，這裡不畫）|
| World Map client `(4,23)` 160×100 ＝ 16,000 px | **逐點相同** |
| Status client `(4,267)` 160×329 | 82.7% 不同——那一片還沒畫，是下一個缺口 |

**不需要任何位移**。這一節原本要求的「找出那個 272 是哪裡來的」到此結案：
落點從來不是遊戲算錯，是這一邊把輸出畫到了錯的地方、又裁掉了大半。

## 5. 怎麼重跑

```sh
nerun -data <原版目錄> -write <可寫目錄> -screen 800x600 \
      -open 'C:\CIV\NEWUNIT.SAV' -script load.txt CIV.EXE
```

`load.txt`：

```
waitfor Load a Saved Game
clickwin Load a Saved Game
run 5000000
clickwin OK
run 400000000
shot ours.png
```

`waitfor`／`clickwin` 用視窗標題而不是座標——**用固定步數或寫死座標等
都不可靠**：同一個畫面在不同輸入下要跑的指令數差好幾倍，而版面會隨字型
度量改變。

`-open` 決定檔案對話框「使用者選了什麼」：把互動換成參數，腳本才能重現。

## 5.1 量「一段時間有多久」時要調 `-clock-us`

`StepClock` 讓虛擬時間跟著**指令數**走（預設 10 µs／指令 ⇒ 10 萬條指令
＝ 1 秒）。這讓執行可重現，但也代表**繪製本身會把時鐘往前推**：任何
「一秒裡有多久在做 X」的量測都會失真。

實例（活動單位閃爍，civ1 的 DS329）：原版的算式是
`GetTickCount()*60/1000 % 60 > 30`，也就是一秒裡藏 483 ms、畫 517 ms。

| `-clock-us` | 量到的藏／畫 |
|---:|---|
| 10（預設）| 250／750 ms |
| 1 | 500／500 ms |

差的那 233 ms 就是一次重畫吃掉的虛擬時間（約 23,000 條指令）。
**週期不受影響**（兩次量到的都是 1 Hz），失真的是佔空比。

> 規則：量週期可以用預設值；**量佔空比、延遲、逾時一定要把
> `-clock-us` 調小再量一次**，兩個值不一致就代表工作量在推時鐘。

## 5.2 `peek`：看執行時的全域

`nedump` 看得到的是**檔案映像**；「這個全域現在是多少」只有跑起來才知道。
腳本的 `peek <sel:off> [len]` 直接印記憶體。

段的選擇器 ＝ `段號 << 3 | 7`（civ1 的 IDA 段名 `dsegN` 就是段號），
段內位移 ＝ 位址 − 段基底。例：civ1 的 `byte_6C31D` 在 `dseg92`
（基底 `0x67D50`）⇒ `peek 02E7:45CD`。

實例：civ1 的 spec 22 §7 第 1 項把一組「runtime 才填的色」列為未知，
`peek 02E7:45BE 16` 一次全部讀出來：

```
00 04 02 06 01 05 03 07 F8 FC FA FE F9 FD FB FF
```

＝ `byte_6C30E`（未探索）0、`byte_6C30F`（海）4、`byte_6C314`（陸）3、
`byte_6C31D` 0xFF——與參考幀上量到的系統色 0／4／3 和活動單位閃爍的純白
完全一致。

## 5.3 已知缺口：Status 面板

三個客戶區裡只有 Status 還對不上（82.7% 不同）。已經定位到的部分：

- 面板的底色由 `sub_5FDC8(rect, 色號)` 畫，色號來自 `byte_6C344`（0x42）
  與 `byte_6C34B`（0x0F，peek 出來的執行時值）。
- `sub_28175(色號)` 在 256 色模式下**不是**建實心筆刷，而是建一張 8×8、
  每個像素都是那個 index 的點陣圖再 `CreatePatternBrush`——這是 Win16
  拿到「就是這一格 index」的標準做法（實心筆刷的 COLORREF 會再經過配色）。
- 這一邊原本把圖樣筆刷當成 `Brush.Index` 用，所以那些區域全變成索引 0
  （黑）。已補上圖樣填色（`DC.FillPattern`，回歸測試
  `TestFillPatternTilesBitmap`）。
- **補上之後 Status 仍是黑的**，所以鏈上還有一環沒找到。下一輪從
  「那兩個 `FillRect` 到底走到哪裡」重新量起。

## 6. 拿它去驗重製版

這一層真正的用途不是「跑得動原版」，是**當重製版的量尺**。三段：

1. `nerun` 跑原版，載入指定存檔，輸出一張 PNG。
2. 重製版跑**同一份存檔**，輸出一張 PNG。
3. `nediff` 逐點比對指定的兩個矩形。

用同一份存檔而不是各自開新局（世界是亂數生成的），用兩個矩形而不是一個
（兩邊的版面不必相同，要比的是畫出來的東西）。腳本在
`scripts/compare-remake.sh`。

### 實測：civ1 的 Go 重製版

```
$ nediff -a-rect 172,62,608,518 -b-rect 172,42,608,518 \
         -ignore 222,251,20,24 civ1go.png oracle.png
比對 608x518 ＝ 314944 個像素：不同 0（0.0000%）
忽略區內另有 54 個像素不同
逐點相同
```

**地圖客戶區 314,944 個像素逐點相同。** 忽略的那 54 個是參考幀上的滑鼠
游標——Windows 畫的，兩邊的渲染器都不畫它。忽略區是**指名的矩形**，
不是放寬容差。

過程裡量到一件重製版那邊的事：第一次比對差 156 個像素，全部在海面上，
而且是同一組顏色互換。那是**海浪的調色盤相位**——重製版有
`-wave-phase` 參數，掃一遍：

| 相位 | 不同的像素 |
|---:|---:|
| 0 | 156 |
| **1** | **0** |
| 2 | 116 |
| 3 | 153 |
| 4 | 196 |

參考幀當時的相位是 1。**這正是對拍該有的產出**：不是「像不像」，
而是「差在哪一個具體的參數上」。
