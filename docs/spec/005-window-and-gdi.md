# 005 — 視窗、訊息與 GDI

## 1. 這一層在做什麼

`internal/win16` 從「一個載好的模組」變成「一個跑得動的 Windows 應用」：
視窗與訊息、裝置內容與繪圖、檔案與資源。它不模擬 Windows 的內部結構，
只實作**應用程式觀察得到的行為**（spec 001 §2）。

## 2. 從 Go 呼叫 16 位元程式碼

視窗程序、對話框程序、列舉回呼都是 16 位元程式碼，而叫它們的是 Go。
`Process.Call16` 的作法是推一個**假的返回位址** `F00E:0000`，
CPU 一跳到那個 selector 就停：

```go
for c.Seg[cpu.CS] != RetTrapSel {
	if err := c.Step(); err != nil { return 0, err }
}
```

`F00E` 不是一塊記憶體，永遠不會被執行，所以不必配置，也不會被誤讀成
程式碼。回來之後暫存器全部還原，只有 `DX:AX` 是輸出。

回呼有步數上限（`CallStepLimit`）。回呼不回來多半是我們給錯了參數，
讓它無聲地跑下去只會把問題推遠。

## 3. 座標：子視窗相對、彈出式絕對

`Window.X/Y` 是**相對父視窗客戶區**的位置——只有 `WS_CHILD` 是這樣；
彈出式視窗（含對話框）雖然也有 owner，位置卻是螢幕座標。`layout` 一次
算完整棵樹的螢幕座標（`AbsX/AbsY`、`ClientX/ClientY`）。

這不是實作細節，是**對錯問題**：CIV.EXE 的對話框建立之後會自己置中
（`MoveWindow`），如果子視窗存的是絕對座標，那六個選單項目會留在原地
——而它們原本的位置在螢幕外。

同一類的坑還有一個：子視窗**沒有標題列**。`WS_CAPTION` ＝
`WS_BORDER｜WS_DLGFRAME`，照頂層規則算的話，18 像素高的自繪控制項會被
扣掉 19 像素的標題列，客戶區高度變成 0——畫面上只是「什麼都沒有」，
不會報錯。`childFrameFor` 分開處理這件事。

## 4. BitBlt：ROP 碼的高位元組就是真值表

GDI 的 32 位元 ROP 碼裡，第 16..23 位是一張三元真值表。對每一個位元平面：

```
結果 = (表 >> ((P<<2) | (S<<1) | D)) & 1
```

照這個做，256 種光柵運算一次到齊，不必一個個特判 `SRCCOPY`／`SRCAND`／
`SRCINVERT`。CIV.EXE 用到的透明貼圖是三段 `SRCINVERT`／`SRCAND`／
`SRCINVERT`（civ1 `docs/re` 的 `draw-prims` 有記），這條路徑因此不必另外寫。

重疊搬移要選對方向，否則同一塊畫布上的捲動會把來源蓋掉；裁切之後要把
同樣的位移套回來源，否則畫出來的東西會整體偏移。兩者都有測試鎖著。

## 5. 調色盤：靜態色佔前十格與後十格

Windows 的 256 色系統調色盤前十格與後十格是應用程式動不了的靜態色，
中間 236 格才給邏輯調色盤。`RealizePalette` 因此從索引 **10** 開始填，
能對上靜態色的直接用靜態色。

這個版面在 civ1 專案那邊**獨立量到過**：它的圖集索引要加 `0x0A` 才是
實體調色盤索引（`docs/re/315` 一族）。兩邊對得起來，所以不是猜的。

畫布存的是**索引**不是 RGB。逐點比對比的是索引，RGB 只在輸出 PNG 時
查表——這讓「和原版逐點相同」有明確的意義，也少掉一層色彩轉換的差異。

## 6. 檔案系統：唯讀根 ＋ 獨立可寫目錄

`Root` 唯讀、`WriteRoot` 才可寫，讀取先看 `WriteRoot`。存檔覆寫原版資料
的情形不會發生（`AGENTS.md`「原版資料不進版控、不被工具改到」）。

檔名比對不分大小寫：DOS 沒有大小寫、Linux 有，不做這一步的話
`CIV.PIC` 在 `civ.pic` 旁邊就找不到。前綴只在**整個路徑元件**相符時
才剝——用字串前綴剝會把 `CIVDATA0.RSC` 剝成 `DATA0.RSC`，而症狀是
「遊戲說找不到自己的資料檔」，看起來像遊戲的問題。這一條有測試鎖著。

## 7. 沒有畫面的時候，讓程式自己說話

這一層有幾個純粹為了診斷而存在的欄位，它們**同時是下一輪的工作清單**：

| 欄位 | 記什麼 |
|---|---|
| `Process.MessageBoxes` | 遊戲彈過的訊息框。它報「資源不足」「找不到檔案」時，這是唯一的管道 |
| `Process.Notes` | 「做了但不完整」的事，去重。靜靜回 0 才是問題 |
| `FileSystem.Opened` | 每一次開檔（成功與失敗都記） |
| `Process.TextOuts` | 畫不出來的字，也是之後接上字型的回歸樣本 |
| `Process.MsgCount` | 每個訊息送過幾次。畫面沒動時最快看出「到底在跑什麼」 |
| `win16.Profile` | CS:IP 抽樣。指令一直在跑但沒有 API 呼叫時，只有這個有用 |

一個實際的例子：`WM_PAINT` 送了 54,876 次而畫面沒動，直接指出
`DefDlgProc` 沒有接上 DLGPROC——視窗程序回 0 之後沒有人做預設處理，
無效區域永遠不會被清掉。

## 8. 「回 0 也看起來正常」的三個實例

這一層踩到的錯有一個共同形狀：**回一個合法但錯的值，畫面只是少了東西，
沒有任何錯誤訊息。**

1. `GetDesktopWindow` 回 0 → 呼叫端拿它去 `GetWindowRect`，RECT 是呼叫端
   的區域變數，裡面是垃圾 → 對話框被擺到 `(8492,-12172)`。
2. `CreateWindow` 的 `hMenu` 對**子視窗**是控制項編號不是選單 → 混在一起
   之後 `GetDlgCtrlID` 一律回 0，`WM_COMMAND` 分不出是哪一個控制項 →
   點主選單沒有反應。
3. `BitBlt` 的參數位元組數手算錯 2 → 1,036 次呼叫全部讀錯位置（spec 004 §3）。

第 2 和第 3 是同一次修好的：改對之後 `BitBlt` 從 0 次變成 1,147 次，
主選單的面板與六個選項符號**第一次出現在畫面上**。

## 10. 點陣字型

`.FON` 本身就是一個 NE，字面放在 `RT_FONT` 資源裡；`CIVFONTS.FON` 裝了
**21 個字面**。真 Windows 是從 `WIN.INI` 的 `[fonts]` 段載入安裝過的字型，
而我們沒有跑安裝程式——所以直接把遊戲目錄裡的 `.FON` 當成「已安裝」。

字形的位元圖是**直行排列**的：寬 W 的字被切成 `ceil(W/8)` 個八像素寬的
直條，每一條連續放 H 個 byte（每個 byte 是那一列的八個像素，最高位在左）。
照一般「由左到右、由上到下」的排法讀，會得到一團長度正確但看起來像雜訊
的資料——這一點有測試鎖著。

兩個容易漏掉的接點：

- **新的 DC 要預設選著系統字型。** 不給預設的話，呼叫端沒有 `SelectObject`
  就直接畫字時，什麼都不會出現。
- **主選單走的是 `DrawText` 不是 `TextOut`。** 兩支都要接；只接一支的話
  畫面上會少掉一整類文字，而且沒有任何錯誤。

`EnumFontFamilies` 的列舉順序就是字型檔裡的順序——civ1 `docs/re/319` 靠
這一點認出 `CIVTIMES18` 是第 17 個字面，所以順序不能亂。
